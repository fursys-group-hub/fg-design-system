# design-qa — 화면 HTML vs 퍼시스그룹 디자인 시스템 정본 검사

생성된 **화면 HTML 파일**이 정본 규격을 지키는지 검사하고, 항목별 통과 여부와 위반 위치(줄)를 표로 보고하는 읽기 전용 워크플로우.

> 피그마 파일과 정본을 대조하던 옛 REST 기반 검사는 성격이 달라 `.claude/skills/_deprecated/design-qa-figma/` 로 분리 보관했다. 이 스킬은 **화면 HTML 파일**만 검사한다.

## 원칙 (필수)

- **화면 HTML 을 수정하지 않는다. 읽기와 보고만 한다.**
- **검사 항목을 이 스킬에 적지 않는다.** 항목은 항상 `design-system/audits/design-qa-checklist.md` 를 **읽어서** 쓴다. 항목이 늘거나 바뀌면 체크리스트 파일만 고치면 되고 이 스킬은 건드리지 않는다.
- 판단이 애매하면 지어내지 말고 `[확인 필요]`로 표시한다.
- 위반·경고가 0건이면 **"clean"으로 명확히** 보고한다.
- 정본 값(색·크기 등)은 외워서 판정하지 않는다. 필요할 때 정본 파일을 로드해 대조한다(§2).

## 현재 정본 기준 (요약)

- **퍼시스그룹 디자인 시스템**(옛 "시디즈 디자인 시스템" 아님).
- **색 22색**(Primary 2톤·브랜드별 / System 10 / Grey 10) **+ Secondary 65색**(고객 화면 전용).
- **타이포 17종** — Title1~8 · Body1~4 · Caption1~5. 고객 화면도 동일하게 쓰며 **별도 Display 계열은 없다**.
- **9개 브랜드**, `<html data-brand="...">` 로 전환.
- **화면 유형 2종** — `data-type="internal"`(업무) / `data-type="customer"`(고객).
- **클래스 접두어** — 업무 `fg-`, 고객 `fgc-`.
- **인터랙션 7종** — `COMPONENTS.html` 하단의 위임 스크립트(체크박스·토스트·탭·페이지네이션·필터접기·사이드바·드롭다운).

> 위 기준은 체크리스트의 "스킬 자체에서 고쳐야 할 옛 기준" 표를 이 스킬에 반영한 것이다. 그 표 자체는 **화면당 검사 항목이 아니라 이 스킬을 최신으로 유지하기 위한 메모**이므로, 검사 실행(§3)에서는 돌리지 않는다.

## 0. 검사 대상 확인

- 사용자가 **검사할 화면 HTML 파일 경로**를 줬는지 확인한다.
- **경로를 안 줬으면** "어느 화면 파일을 검사할까요? 경로를 알려주세요."라고 **묻고 중단**한다. 임의로 파일을 고르지 않는다.
- 경로를 여러 개 주면 각각 검사한다.
- 대상 파일 최상단 `<html ...>` 태그에서 **`data-brand` 와 `data-type` 을 먼저 읽는다.** `data-type` 값(internal/customer)으로 검사 분기를 정한다. (이 두 속성의 존재 자체도 체크리스트의 "필수 속성" 항목이다.)

## 1. 체크리스트 로드

- `design-system/audits/design-qa-checklist.md` 를 **읽는다.**
- 검사에 쓰는 표는 **두 개**다:
  - **"기계가 잡을 수 있는 것"** 표 → 실패 시 **위반**으로 분류.
  - **"사람이 봐야 하는 것"** 표 → 실패/의심 시 **경고**로 분류(위반 아님, 사람 판단 여지를 남긴다).
- **"스킬 자체에서 고쳐야 할 옛 기준"** 표는 검사 항목이 아니므로 **검사에서 제외**한다(§ 현재 정본 기준 참조).

## 2. 정본 값 로드 (필요할 때만)

체크리스트 항목 중 정본 값과 대조해야 하는 것(임의 hex·임의 크기 등)을 위해, 필요 시 아래를 로드한다.

- 색(22색 + Secondary 65) → `dist/fg/tokens.css` 의 CSS 변수(`--fg-color-*` · `--fg-secondary-*`) 또는 `design-system/tokens/color.md`.
- 타이포 17종 크기 → `design-system/tokens/typography.md` 또는 `tokens.css`.
- 클래스·구조 규칙 → `dist/fg/CLAUDE.md`(또는 `design-system/CLAUDE.md`).
- 브랜드별 값은 `data-brand` 블록 기준. 값을 외워서 판정하지 않는다.

## 3. 검사 실행

- 체크리스트 **각 행의 "무엇을 보는가"** 설명을 대상 화면 파일에 그대로 적용한다.
- 각 항목마다 **통과 / 실패 / 해당 없음**을 판정하고, 실패면 **파일에서 몇 번째 줄인지**(라인 번호)를 확보한다. `grep -n` 등으로 실제 줄을 찾는다(줄 번호를 추정하지 않는다).
- `data-type` 유형상 해당되지 않는 항목(예: 고객 화면 전용 항목을 internal 화면에서)은 **"해당 없음(—)"** 으로 둔다.
- 기계 항목은 규칙 위반을 명확히 판정한다. 사람 항목은 확정하지 말고 **경고**로 표시해 최종 판단을 사람에게 남긴다.
- 값 판정이 불확실하면 `[확인 필요]`로 표시한다.

## 4. 보고 (표)

검사 결과를 **한 표**로 보여준다. 열은 **항목 / 통과 여부 / 위반 줄** 세 칸이다.

| 항목 | 통과 여부 | 위반 줄 |
|---|---|---|
| (체크리스트 "기계가 잡을 수 있는 것" 각 행) | ✅ 통과 / ❌ 위반 / — 해당없음 | 위반한 파일 라인 번호(복수면 나열), 통과·해당없음이면 빈칸 |
| (체크리스트 "사람이 봐야 하는 것" 각 행) | ✅ 통과 / ⚠️ 경고 | 근거 라인 번호 |

- **기계 항목 실패 = ❌ 위반**, **사람 항목 실패/의심 = ⚠️ 경고**로 구분한다.
- 위반 줄에는 대상 화면 파일의 **라인 번호**를 적는다(여러 개면 `12, 45, 78`처럼).
- 표 위에 대상 파일명 · `data-brand` · `data-type` 을 한 줄로 밝힌다.

## 5. 요약 (필수, 한 줄)

표 아래에 **한 줄 요약**을 넣는다:

> **위반 N개 · 경고 M개** (대상: `<파일명>`, 유형 `<internal/customer>`) — 둘 다 0이면 **clean**.

`[확인 필요]`가 있으면 개수를 함께 적는다.

## 6. 저장 (요청 시에만)

- 사용자가 결과 저장을 원하면 `design-system/audits/qa-{화면명}-{YYYY-MM-DD}.md` 로 저장한다(없으면 디렉터리 생성). 상단에 대상 경로·유형·검사일을 기록한다.
- **커밋은 사용자 승인 시에만.** 승인 시 한국어 커밋 메시지 + 끝에:
  `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`
