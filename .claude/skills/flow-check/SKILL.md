# flow-check — 화면 HTML 이 실제 상황을 견디는지 검사

생성된 **화면 HTML 파일**이 데이터가 있을 때만 그려진 화면이 아닌지 검사하고, 항목별 통과 여부와 위반/경고 위치(줄)를 표로 보고하는 읽기 전용 워크플로우.

## design-qa 와 무엇이 다른가

- **design-qa 는 규칙을 지켰는지 본다.** 색·크기·마크업이 정본과 맞는지 기계적으로 대조한다. "이 화면이 규격대로 만들어졌나".
- **flow-check 는 화면이 실제 상황을 견디는지 본다.** 데이터가 있을 때만 그려진 화면이 아닌지 확인한다. "목록이 비어 있는 날, 글자가 유난히 긴 경우, 저장이 실패하는 순간에도 버티나".
- 둘은 성격이 다르므로 **서로를 대체하지 않는다.** 규격이 완벽해도 빈 목록 문구가 없으면 flow-check 에서 걸리고, 흐름이 완전해도 임의 hex 를 쓰면 design-qa 에서 걸린다. 화면을 만든 뒤 **둘 다** 돌리는 것을 권한다.

## 원칙 (필수)

- **이 저장소에는 아무것도 쓰지 않는다.** 검사 결과 저장도, 커밋도, 푸시도 사용자에게 제안하지 않는다. 저장은 저장소 밖 `~/Desktop/fg-output` 아래에만 한다.
- **화면 HTML 을 수정하지 않는다. 읽기와 보고만 한다.** 저장소 파일도 고치지 않는다.
- **검사 항목을 이 스킬에 적지 않는다.** 항목은 항상 `design-system/audits/flow-check-checklist.md` 를 **읽어서** 쓴다. 항목이 늘거나 바뀌면 체크리스트 파일만 고치면 되고 이 스킬은 건드리지 않는다.
- 판단이 애매하면 지어내지 말고 `[확인 필요]`로 표시한다.
- 위반·경고가 0건이면 **"clean"으로 명확히** 보고한다.
- **없음을 증명하는 검사가 많다**(빈 상태 문구가 "없는지", 확인 단계가 "없는지"). 근거를 `grep -n` 등으로 확인하고, 못 찾았으면 "못 찾음"이라고 정직하게 적는다. 있는데 못 본 것과 아예 없는 것을 구분한다.

## 0. 검사 대상 확인

- 사용자가 **검사할 화면 HTML 파일 경로**를 줬는지 확인한다.
- **경로를 안 줬으면** "어느 화면 파일을 검사할까요? 경로를 알려주세요."라고 **묻고 중단**한다. 임의로 파일을 고르지 않는다.
- 경로를 여러 개 주면 각각 검사한다.
- 대상 파일 최상단 `<html ...>` 태그에서 **`data-brand` 와 `data-type` 을 먼저 읽는다.** `data-type` 값(internal/customer)으로 검사 분기를 정한다(빈 목록·오류 입력·저장 결과는 주로 업무 화면 맥락이다).

## 1. 체크리스트 로드

- `design-system/audits/flow-check-checklist.md` 를 **읽는다.**
- 검사에 쓰는 표는 **세 개**다:
  - **"기계가 잡을 수 있는 것"** 표 → 실패 시 **위반**으로 분류.
  - **"사람이 봐야 하는 것"** 표 → 실패/의심 시 **경고**로 분류(위반 아님, 사람 판단 여지를 남긴다).
  - **"아직 정본에 규칙이 없는 것"** 표 → **경고**로만 분류(정본에 규칙이 없어 위반으로 판정할 근거가 없다).

## 2. 정본 참조 (필요할 때만)

판정 근거를 대야 할 때만 아래를 로드한다. 값을 외워서 판정하지 않는다.

- 표 셀 nowrap·표 밖 긴 텍스트 처리 규칙 → `dist/fg/CLAUDE.md`(「Table 구조」).
- 토스트(결과 알림)·인풋 오류 등 컴포넌트 마크업 → `dist/fg/COMPONENTS.html` · `dist/fg/fg-components.css`.
- 로딩 상태는 **정본에 사용 규칙이 없다.** Loader 아이콘은 `dist/fg/icons.md`(3종)에 있으나 언제·어떻게 쓰는지가 미정이므로 **경고로만** 알린다.

## 3. 검사 실행

- 체크리스트 **각 행의 "무엇을 보는가"** 설명을 대상 화면 파일에 그대로 적용한다.
- 각 항목마다 **통과 / 실패 / 해당 없음**을 판정하고, 실패면 **파일에서 몇 번째 줄인지**(라인 번호)를 확보한다. `grep -n` 등으로 실제 줄을 찾는다(줄 번호를 추정하지 않는다). 상태가 아예 없어 "못 찾음"이면 그 취지를 위반 줄 칸에 적는다.
- `data-type` 유형상 해당되지 않는 항목은 **"해당 없음(—)"** 으로 둔다.
- 기계 항목은 규칙 위반을 명확히 판정한다. 사람 항목·정본 없음 항목은 확정하지 말고 **경고**로 표시해 최종 판단을 사람에게 남긴다.
- 값 판정이 불확실하면 `[확인 필요]`로 표시한다.

## 4. 보고 (표)

검사 결과를 **한 표**로 보여준다. 열은 **항목 / 통과 여부 / 위반 줄** 세 칸이다.

| 항목 | 통과 여부 | 위반 줄 |
|---|---|---|
| (체크리스트 "기계가 잡을 수 있는 것" 각 행) | ✅ 통과 / ❌ 위반 / — 해당없음 | 위반한 파일 라인 번호(복수면 나열), 통과·해당없음이면 빈칸. 상태가 없어 못 찾았으면 "없음" |
| (체크리스트 "사람이 봐야 하는 것" 각 행) | ✅ 통과 / ⚠️ 경고 | 근거 라인 번호 |
| (체크리스트 "아직 정본에 규칙이 없는 것" 각 행) | ⚠️ 경고 | 근거 라인 번호(있으면) |

- **기계 항목 실패 = ❌ 위반**, **사람 항목 실패/의심 = ⚠️ 경고**, **정본 없음 항목 = ⚠️ 경고**로 구분한다.
- 위반 줄에는 대상 화면 파일의 **라인 번호**를 적는다(여러 개면 `12, 45, 78`처럼).
- 표 위에 대상 파일명 · `data-brand` · `data-type` 을 한 줄로 밝힌다.

## 5. 요약 (필수, 한 줄)

표 아래에 **한 줄 요약**을 넣는다:

> **위반 N개 · 경고 M개** (대상: `<파일명>`, 유형 `<internal/customer>`) — 둘 다 0이면 **clean**.

`[확인 필요]`가 있으면 개수를 함께 적는다.

## 6. 저장 (요청 시에만)

- 사용자가 결과 저장을 원하면 `~/Desktop/fg-output/flow-{화면명}-{YYYY-MM-DD}.md` 로 저장한다(없으면 디렉터리 생성). 상단에 대상 경로·유형·검사일을 기록한다.
